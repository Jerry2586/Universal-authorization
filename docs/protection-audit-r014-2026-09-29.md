## F01：文件完整性缺少不可由包持有人重算的内容签名（优先修复）

代码位置：

- `apps/build-worker/src/engine.js:36`：逐文件摘要及保护信息被组织为 HMAC 输入。
- `apps/build-worker/src/engine.js:50`：HMAC 使用 Package Secret。
- `apps/build-worker/src/runtime.js:907`：运行时配置包含恢复 Package Secret 的分片与顺序。
- `apps/license-api/src/modules/packaging/authorization-service.js:22`：中心签名声明仅包含签发方、类型、产品、构建、包、版本、域名、水印和签发时间；不包含最终文件清单摘要。
- `apps/build-worker/src/engine.js:397`：成品校验验证身份签名、文件摘要和该 HMAC。

本地实验：

1. 原包通过 `verifyArtifact`。
2. 在一个 CSS 文件末尾添加无业务影响的审计注释，校验拒绝：`PACKAGE_FILES_TAMPERED`。
3. 保持原包身份签名不变，仅使用包内可恢复材料更新文件摘要与 HMAC，校验通过。
4. 同时改变清单与预期域名，但保留原签名，校验拒绝：`PACKAGE_MANIFEST_TOKEN_INVALID`。

结论：当前校验能够发现没有同步重算校验值的修改，但不能把该 HMAC 当作对抗包持有者篡改的独立信任依据。实验没有伪造中心签名，也没有证明绕过在线激活、暂停、撤销或生产系统接口。Worker 完成接口仍另有租约、构建身份、包 proof、Install Key 等约束（`modules/packaging/service.js:189`），此次未尝试绕过这些约束。

修复目标：在最终构建完成后，由授权中心受控签名流程签署规范化内容清单摘要，覆盖业务资源、运行时、桥 ZIP 与关键身份/保护字段；校验信任锚必须来自受信任配置，不能接受包任意自带公钥就当作受信任发布者。设计明确的签名排除项，避免清单/签名自引用。新包的格式与签名必须强制校验，旧包升级采用明确兼容规则，不能以静默回退方式放过新包缺失签名。

## F02：AES 加密与包持有者保密是两个不同边界

`engine.js:59` 以 Package Secret 派生 AES 密钥；`runtime.js:203` 在浏览器中使用同一材料解密。`manifest.js:22` 与 `runtime.js:917` 交付了分片及重排信息。

本次在没有中心私钥、固定 Key、Install Key 的情况下，仅用原 ZIP 解密身份文件成功。此现象符合当前浏览器解密设计，不能描述为 AES 算法被破解。身份中的主要业务字段也已写入明文清单。

修复目标：把 Package Secret 按可被包持有人取得的包级凭据设计；不可把它提升为管理员、安装身份私钥、固定授权 Key 或发布签名权限。若要求业务逻辑对客户服务器管理员也保密，必须另行评估服务端托管范围及其联网依赖，不在本轮悄然改变部署产品。

## F03：运行时、桥前端与业务 JS 的保护流程不一致

`engine.js:241` 先混淆源文件，然后才生成并加入运行时；`runtime.js:930` 直接输出函数正文与 Base64 配置。`xboard-bridge-package.js:10` 直接收集桥模板文件，`xboard-bridge-package.js:30` 将其打包。

修复目标：对生成后的授权运行时、桥前端 JS 统一执行兼容的压缩与混淆，并明确处理内联脚本。保留公开接口、必要全局符号及两阶段激活行为；混淆失败即停止构建。混淆提高阅读成本，但不替代 F01 的签名或中心授权判断。

业务混淆器当前保留部分函数/类名、不开启全局重命名和控制流平坦化（`engine.js:114`、`:124`）。这些是兼容与性能取舍，不能承诺所有变量/函数名都已不可读，也不能直接用“开启最强选项”代替兼容性测试。

## 不改动的授权语义

- 固定 Key 与一次性 Install Key 不合并、不替换。
- 本地安装阶段、在线授权阶段及 60 分钟窗口按现有约定保留。
- 免费与付费授权均继续服从中心的暂停、撤销与域名/安装身份限制。
- 桥上的注册、挑战签名、私有状态读写继续要求管理员权限（`AppgogLicenseBridge/routes/api.php`）。
- 不引入 Xboard 无法解压的密码 ZIP，也不把整个 PHP 桥改为依赖未经约定的专有加载器。
- 保护加固不得破坏首次安装、旧桥升级、已激活刷新无闪屏、正常原生后台修复入口与客户数据保留。
