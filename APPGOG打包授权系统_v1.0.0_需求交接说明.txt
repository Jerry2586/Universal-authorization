最高优先级：最后核对需求统一结论
======================================================================

本节集中表达用户最后连续确认的全部想法，是全文最高优先级的开发总纲。后文若与本节存在冲突，一律以本节为准；旧代码、旧文档和旧聊天中的早期方案均不能覆盖本节。

一、整体重构，不再继续堆补丁

- 正式系统名统一为“APPGOG打包授权系统”，目标版本统一为“v1.0.0”。
- 在现有授权逻辑、打包逻辑、加密/混淆方法和部署能力基础上整体重新梳理、总结并重构。
- 现有功能不能凭感觉保留或删除：必须先用代码、数据迁移和测试核验；确实可用的继续用，不能用、重复、过时、伪安全或职责错误的删除或替换。
- “整体重新制作”不等于清空仓库，也不等于把旧代码原样包装；目标是保住真实有效的根基，重新形成统一、可测试、可部署、可维护的完整系统。

二、最终 Key 模型必须分清

- 固定 License Key：商家发给客户的长期购买身份。用于登录打包中心、进入客户中心、绑定/管理授权域名、创建专属构建，并在 APPGOG 后台完成正式激活。固定 Key 不随每次打包变化。
- 一次性 Install Key：每个客户专属 ZIP 单独生成，只与对应 Build/Package 匹配，只负责第一阶段安装解锁；验证成功后立即作废，不能再次用于其他包或环境。
- Package Secret/每包内部密钥：每次构建随机生成，客户不可见，用于离线认包、文件归属、完整性保护和每包差异化保护；它不是客户输入的一次性 Install Key。
- Activation Token/正式激活凭证：第二阶段成功后由授权服务器签发，用于后续本地验签和授权状态刷新；具体算法由安全评审确定。

三、最终流程是“两阶段、两层锁”，不能合并

第一阶段——安装解锁：

1. 客户使用固定 Key 登录打包中心并绑定授权业务域名。
2. 客户创建构建；系统生成独立 Build ID、Package ID、每包内部密钥、客户专属 ZIP 和对应的一次性 Install Key。
3. 客户把 ZIP 上传到 Xboard 安装。
4. 安装阶段只输入一次性 Install Key。
5. 系统验证 Install Key、包身份和安装环境；成功后记录安装解锁凭证并立即消费该 Key。
6. 此时只是“包已解锁/可安装”，APPGOG 正式功能仍然锁定。

第二阶段——后台正式激活：

1. 用户首次进入 APPGOG 后台，只能看到激活入口，主题设置和 APPGOG 与 Xboard 的关键连接不可用。
2. 用户在后台输入长期固定 License Key。
3. 授权服务器验证固定 Key、客户、绑定域名、Build/Package、安装解锁凭证、Xboard Origin、Installation ID、版本和授权状态。
4. 验证成功后签发正式激活凭证，才开放主题设置、当前主题、APPGOG 与 Xboard 的接口和完整业务功能。

明确覆盖关系：早期曾出现“固定 Key 与一次性 Install Key 在同一表单同时输入”的整理，这是已经被后续核对纠正的旧方案，禁止实施。

四、激活保护必须是真正的服务端限制

- 未激活时不能只隐藏按钮或修改前端文案。
- 读取/保存 APPGOG 设置、启用主题、调用 Xboard 关键接口、加载受保护资源、执行核心业务和获取正式更新等服务端入口必须统一检查激活状态。
- 用户即使手工显示按钮、修改前端或直接请求 URL，也不能绕过授权守卫。
- 包、Key、域名、Origin、Installation ID 或正式凭证不匹配时必须拒绝。

五、文件保护目标与现实边界

- 目标是让直接提取看不到易读完整源码、拆走部分文件不能单独使用、复制到其他域名/环境不能直接运行，同时提高逆向成本并能追踪泄漏包。
- 保护方向包括每包随机混淆、字符串/控制流保护、模块拆分、关键资源加密载荷、签名/完整性清单、环境绑定和构建水印。
- ZIP 必须保持合法并能被 Xboard 正常安装，不能真的做成损坏文件。
- 不得虚假承诺“绝对无法破解”或“运行态永远无法提取”；客户控制服务器或浏览器时，专业攻击者仍可能截获运行态内容。
- 具体算法和工具必须经过安全性、兼容性、性能和可维护性评审，不能把助手曾举例的某个算法当成用户锁死的唯一方案。

六、两个管理中心的职责是写死的，不得改变

- Web 授权中心只管理授权业务：客户、产品、版本、固定 Key、客户授权域名、打包、Build/Package、一次性 Install Key、正式激活、业务审计。
- Linux APPGOG 管理中心只管理系统架设、运行和整体安全：Linux 环境、Docker、反向代理、平台域名、DNS、HTTPS/SSL、证书、服务、数据库健康、Worker/队列健康、更新、备份、恢复、日志、诊断和文件权限。
- Linux 菜单可以查看业务服务是否健康，但不能签发/停用客户 Key、修改客户授权域名、发布业务版本、消费 Install Key、修改激活记录或直接编辑业务数据库。
- “客户授权域名”属于授权中心；“授权中心平台域名和打包中心平台域名”属于 Linux 运维管理，二者不能混淆。

七、生产部署统一 Docker，删除面板路线

- 新 Linux 服务器应能通过一条命令自动完成环境检测、Docker/Compose 安装、正式发布包下载与校验、配置、启动、HTTPS 和健康检查。
- 安装完成后提供专业、可重复打开的 Linux 管理菜单，至少覆盖系统状态、两个平台域名、DNS、SSL/证书、服务、日志、更新、备份、恢复、诊断与安全检查。
- 删除并停止维护宝塔、aaPanel、1Panel 等面板部署入口、面板 Docker 编排、面板反向代理/证书流程及面板更新教程；正式生产安装、更新和恢复只有统一 Docker 路线。
- Caddy、具体安装目录、Compose 最低版本和全局命令路径属于实现选择/现有方案，先核验再确定，不是用户锁死的业务要求。

八、现状与目标必须分开

- 旧聊天曾报告一键安装脚本、Linux 菜单和部分 Docker 管理能力已实现，但必须重新检查当前仓库和 Git 才能确认。
- 当前旧代码曾被核验为：已有部分授权状态、签名和轻量包身份能力，但还不是完整的两阶段安装/正式激活，也没有完整独立的 Install Receipt；现有 JS 保护主要不是完整密码学加密或真正的高强度混淆。
- 新开发必须明确列出“已实现、部分实现、未实现、验证后保留、验证后删除/替换”，禁止把目标设计写成当前已完成功能。

九、最后交付目标

- 新聊天先完整读本文件，再盘点真实代码、数据库、API、前端、构建 Worker、部署脚本、测试、文档和未提交改动。

二、系统定位
======================================================================

APPGOG打包授权系统是一套面向 APPGOG/Xboard 主题或扩展产品的授权、客户打包、安装激活和平台运维系统。

系统不是简单的“输入 Key 下载 ZIP”，而是完整链路：

客户购买授权
  → 获得长期固定 License Key
  → 使用固定 Key 登录打包中心
  → 在客户中心绑定授权域名
  → 选择允许的产品版本并创建构建
  → 系统为本次构建生成独立 Build/Package 身份
  → 生成客户专属 ZIP 和与该 ZIP 对应的一次性 Install Key
  → 客户将 ZIP 安装到 Xboard
  → 安装阶段只输入一次性 Install Key，验证包与环境后完成第一层解锁，Key 立即作废
  → APPGOG 仍保持受限/锁定
  → 首次进入后台再输入固定 License Key 完成正式激活
  → 授权中心验证客户、域名、包、安装环境和授权状态
  → 签发带签名的 Activation Token/等效正式凭证
  → 激活后才开放 APPGOG 与 Xboard 的正式连接和功能
  → 后续本地验签运行并周期性联网刷新授权状态

三、不可改变的架构边界
======================================================================

以下两个中心的职责必须永久分开，不能因为菜单方便而混合。

（一）Web 授权中心：只管理授权业务

负责：

- 客户管理；
- 产品和主题版本管理；
- 上传、发布、停用、回滚产品版本；
- License Key 签发、查询、停用、恢复和轮换；
- 客户授权域名绑定和迁移；
- 客户打包权限、版本权限，以及最终确认采用的构建限制策略；
- 构建任务、Build ID、Package ID、Package Secret；
- 一次性 Install Key 的生成、匹配、消费和作废；
- 激活记录、Activation Token 和授权状态；
- Worker 的业务节点凭证及任务调度；
- 授权、打包、激活统计与业务审计。

固定定义：

授权中心 = 客户 + 产品 + 版本 + 打包 + Key + 激活 + 授权业务

（二）Linux APPGOG 管理中心：只管理系统运行、部署和安全

负责：

- Linux 环境检查；
- Docker Engine、Buildx、Docker Compose 安装和版本检查；
- Docker Compose 服务生命周期；
- 反向代理、平台域名、DNS、HTTPS 和证书（Caddy 是候选/现有实现之一）；
- 授权中心平台域名与打包中心平台域名；
- 防火墙、端口、磁盘、内存和网络检查；
- 服务启动、停止、重启、更新和版本回滚；
- 数据库、数据卷、Worker、队列的健康检查；
- 完整备份和恢复；
- 日志、诊断报告、安全修复、文件权限；
- 签名密钥文件是否存在及权限是否正确；
- 容器和整套系统的运行安全状态。

固定定义：

Linux 管理中心 = 安装 + 环境 + Docker + 平台域名 + HTTPS
                 + 系统安全 + 更新 + 备份 + 恢复 + 诊断

Linux 菜单只能显示业务服务健康状态，不能直接签发 License Key、创建客户、修改客户授权域名、修改构建额度、发布主题版本、消费 Install Key、修改激活记录或直接编辑业务数据库。

容易混淆但必须分开的内容：

- 授权中心管理“客户授权域名”；Linux 菜单管理“平台自己的授权中心域名和打包中心域名”。
- 授权中心管理 Worker 的业务凭证和任务；Linux 菜单管理 Worker 容器和资源是否健康。
- 授权中心管理数据库业务记录；Linux 菜单只检查、备份和恢复数据库，不直接编辑业务数据。

======================================================================
四、三类 Key 与内部激活凭证
======================================================================

（一）固定 License Key

这是客户的长期购买身份和打包中心登录凭证，不随每次构建变化。

用途：

- 登录客户打包中心；
- 识别客户、产品和授权状态；
- 查看、首次绑定授权域名；
- 创建构建、查看进度和历史构建；
- 下载专属 ZIP；
- 查看对应的一次性 Install Key；
- 查看授权、版本和更新期限；
- 按安全流程轮换固定 Key。

轮换固定 Key 后，旧 Key 应立即停止登录和创建新构建；已经激活的安装如何处理，应依据 License generation 和授权刷新策略明确实现。

（二）Package Secret / 每包内部内容密钥

每次构建独立生成，客户不可见，用于离线识别同一个包内文件之间的关系。它不是固定 Key，也不是客户输入的一次性 Install Key。用户早期所说“临时 Key 与包对应、无需联网认包”在工程上应拆成两种职责：客户可见的一次性 Install Key 负责第一阶段安装解锁；客户不可见的 Package Secret/包身份负责离线认包与文件保护，二者不得混用或暴露。

每次构建至少生成：

- Build ID；
- Package ID；
- Package Secret；
- 产品和版本信息；
- 客户授权标识；
- 构建清单；
- 文件完整性摘要；
- 构建水印/追踪信息。

包身份用于离线判断文件是否属于同一构建、清单或文件是否被替换、删除、拼接，以及本地激活凭证是否属于当前包。

Package Secret 不能代替在线激活，因为复制完整 ZIP 时包内信息也会被复制。

（三）一次性 Install Key

每个客户专属 ZIP 对应一个独立的一次性安装 Key：

ZIP A → Install Key A
ZIP B → Install Key B

匹配规则：

- ZIP A + Install Key B：拒绝；
- ZIP A + 其他客户的固定 Key：拒绝；
- ZIP A + 已消费的 Install Key A：拒绝；
- ZIP A + 正确 Install Key A：只完成第一阶段安装解锁；
- 第一阶段成功后，Install Key 必须在数据库事务中立即作废，不能再次解锁其他环境；
- 正式功能仍保持锁定，必须进入后台完成第二阶段固定 License Key 激活。

（四）Activation Token

这是服务器签发、用户通常不可见的正式激活凭证。

至少绑定：

- License ID；
- License generation；
- Build ID；
- Package ID；
- 产品代码和版本；
- 授权域名；
- Xboard 后台 Origin；
- Installation ID；
- 签发时间、过期时间和离线期限；
- 经过安全评审选定的非对称数字签名（Ed25519 是候选方案，不是用户锁定的唯一算法）。

固定 Key 不应完整明文保存在浏览器 LocalStorage。服务端也应只保存验证所需的哈希或加密数据。

======================================================================
五、客户中心与域名绑定
======================================================================

客户使用固定 License Key 登录后进入专属用户中心，而不是普通下载页。

客户中心至少显示：

- 授权产品：APPGOG；
- 授权状态；
- 脱敏后的固定 Key；
- 绑定域名；
- 更新截止时间；
- 当前可用版本；
- 今日剩余构建次数；
- 构建任务进度；
- 历史构建、下载和一次性安装 Key；
- 域名迁移状态。

允许客户：

- 查看自己的授权；
- 首次绑定自己的授权域名；
- 选择被授权的版本；
- 创建和查看构建任务；
- 下载自己的专属包；
- 查看自己构建对应的一次性 Install Key；
- 在规则允许时重新构建；
- 发起受控的域名迁移。

禁止客户：

- 查看或修改其他客户的数据和域名；
- 查看 Package Secret、签名私钥或完整内部 License ID；
- 为未授权域名创建构建；
- 将固定 Key 用于其他产品；
- 绕过版本、额度或授权状态限制。

域名首次绑定流程：

固定 Key 登录 → 输入业务域名 → 规范化域名 → 确认绑定 → 建立长期关系 → 以后只为该域名构建。

域名应规范化，例如 https://WWW.Example.com/ 统一为 example.com。后续换域名必须走明确的迁移、验证和审计流程，不能在普通构建页随意修改。

======================================================================
六、构建与打包流程
======================================================================

每次构建必须是客户、授权、域名、产品版本和包身份共同决定的专属构建。

构建流程：

1. 验证固定 Key、客户、产品授权和授权状态。
2. 验证绑定域名、版本范围、更新期限，以及系统最终确认采用的构建限制策略。
3. 创建不可猜测的 Build ID 和 Package ID。
4. 生成独立 Package Secret、构建水印和完整性清单。
5. 对关键 JS/资源执行每包随机化的压缩、混淆、字符串保护、路径/文件名变化或加密载荷处理。
6. 生成合法、可由 Xboard 正常上传安装的 ZIP。
7. 生成与本 ZIP 严格对应的一次性 Install Key。
8. 保存构建状态、摘要、制品哈希和审计记录。
9. 客户只能访问自己的任务和制品。

构建必须可追踪、可明确显示失败原因，并防止并发生成或消费重复的一次性 Key。每日额度、自动重试和旧版本重新构建属于候选产品策略，实施前需结合现有逻辑确认，不能当作用户已经锁定的规则。

======================================================================
七、Xboard 安装与两阶段激活
======================================================================

最终确认的是两个阶段、两层锁，不能合并为一个同时输入两个 Key 的表单。

第一阶段：安装解锁

1. 客户将专属 ZIP 上传到 Xboard 并开始安装。
2. 安装流程只要求输入与该 ZIP 对应的一次性 Install Key。
3. 系统验证 Install Key、Build ID、Package ID、包身份和当前安装环境。
4. 成功后生成本地 Install Receipt/等效安装解锁凭证，并在事务中立即消费一次性 Install Key。
5. 此时状态为 package_unlocked（名称可按现有代码调整），只表示该包可在本环境完成安装，不代表 APPGOG 已正式激活。

第二阶段：后台正式激活

1. 安装完成后 APPGOG 仍保持锁定。
2. 用户首次进入 APPGOG 面板，在后台激活入口输入长期固定 License Key。
3. 授权服务器验证固定 Key、绑定域名、包身份、Xboard Origin、Installation ID、版本和授权状态。
4. 成功后签发正式 Activation Token/等效凭证，状态才变为 activated，并接通 APPGOG 与 Xboard。

未激活状态：

- 显示 APPGOG 名称和版本；
- “主题设置”替换为“激活 APPGOG”；
- “当前主题”等正式入口禁用；
- 不加载完整管理页面、受保护配置和核心业务模块；
- 直接访问正式设置 URL 时跳回激活页；
- 服务端所有关键接口仍必须拒绝，不能只靠 CSS 或前端隐藏。

两个阶段均应由系统自动检测所需环境信息，而不是完全信任用户手填。可检测并展示：

- 当前授权业务域名；
- Xboard 后台地址/Origin；
- Installation ID；
- Build ID 与 Package ID。

第一阶段安装解锁至少验证：

1. Install Key 是否存在、未消费且属于当前 Build；
2. Build、Package 和包身份是否一致；
3. 当前安装环境是否符合要求；
4. 请求是否存在重放、并发消费或篡改风险。

第二阶段正式激活至少验证：

1. 固定 Key 是否存在、有效且属于 APPGOG；
2. 固定 Key 是否属于当前客户和当前授权域名；
3. 已存在有效的本地安装解锁凭证，并且它属于当前 Build/Package/环境；
4. Build、Package、License 和产品版本是否一致；
5. 包身份/完整性证明是否正确；
6. 当前域名、后台 Origin 和 Installation ID 是否符合要求；
7. 授权是否停用、过期、超过激活数量或超出版本范围；
8. 请求是否存在重放或篡改风险。

第一阶段成功时消费 Install Key；第二阶段成功时创建正式激活记录并签发 Activation Token。两笔业务不能混成一次提交。

激活后才允许：

- 注册和使用 APPGOG 与 Xboard 的正式连接；
- 进入主题设置和当前主题；
- 读取和保存正式配置；
- 加载完整 JS 和受保护资源；
- 调用关键后台接口；
- 启用营销弹窗等业务模块；
- 执行授权范围内的定时任务；
- 获取正式版本更新。

所有关键服务端接口都必须经过统一授权守卫。即使用户手工恢复按钮或直接调用 URL，服务端也应返回统一的未激活错误，例如 APPGOG_NOT_ACTIVATED。

======================================================================
八、联网与离线边界
======================================================================

- 固定 Key 登录客户中心：必须联网；
- 创建构建和下载授权制品：必须联网；
- 第一阶段消费一次性 Install Key：必须联网；
- 第二阶段使用固定 License Key 正式激活：必须联网；
- 包内部完整性和包身份识别：可离线；
- 激活后正常运行：允许在签名凭证有效期和离线宽限期内本地验签运行；
- 授权状态：必须周期性联网刷新；
- 授权服务器短暂故障：宽限期内不应让全部客户网站立即失效；
- 超过离线宽限期仍不能验证：进入明确的受限或锁定状态。

所有时间、重试、撤销、宽限和恢复策略必须可测试，并避免单纯依赖客户端系统时间。

======================================================================
九、文件保护的目标与现实边界
======================================================================

目标：防止普通复制、直接读取完整源码、拆走少量文件直接使用、跨域名复制激活，增加逆向成本，并能追踪泄漏包。

可采用：

- JavaScript 压缩和标识符混淆；
- 控制流混淆和字符串保护；
- 模块拆分、每包随机文件名/路径/变量；
- 关键资源加密载荷；
- 从 Package Secret 和包身份派生保护数据；
- 签名构建清单和文件完整性校验；
- 客户、License、Build 级水印；
- 激活后才允许加载关键模块；
- 服务端接口再次验证授权。

复制和篡改的预期结果：

- 复制部分文件：缺少清单或包关系，完整性验证失败；
- 复制完整 ZIP 到其他域名：Activation Token 域名不匹配；
- 复制完整目录和凭证到其他环境：Origin 或 Installation ID 不匹配；
- 修改 Token：签名验证失败；
- 使用其他包的一次性 Key：Build/Package/License 不匹配。

必须诚实保留现实边界：只要代码最终在客户控制的服务器或浏览器执行，就无法承诺绝对不可提取或绝对不可破解。ZIP 必须保持合法，不能用“损坏 ZIP”的方式制造乱码，否则 Xboard 也无法安装。正确目标是让静态提取看到密文或难读代码、提高破解成本和可追踪性，而不是承诺数学意义上的永久不可提取。

十、Linux/Docker 一键安装与专业菜单
======================================================================

已确认目标体验：在一台新 Linux 服务器上复制一条命令，自动完成环境、Docker 和系统安装；安装后通过简洁的全局命令打开专业管理菜单。

生产部署路线统一为 Docker。删除并停止维护宝塔、aaPanel、1Panel 等面板部署入口、面板 Docker 编排、面板反向代理/证书流程和面板更新教程；它们不再作为正式安装、更新或恢复路径。菜单中的“系统更新”指 APPGOG 统一 Docker 部署的版本更新，不是面板更新。

安装器应：

1. 识别受支持的 Linux 发行版和 CPU 架构；
2. 安装或验证 Docker Engine 和 Docker Compose；是否需要 Buildx 及最低版本由现有构建方式和兼容性核验决定；
3. 检查网络、磁盘、端口和防火墙；
4. 获取并校验正式发布包，禁止把私有 Git Token 放进命令历史；
5. 询问或接收授权中心平台域名和打包中心平台域名；
6. 检查 DNS 是否指向当前服务器；
7. 创建固定安装目录和权限；
8. 生成高强度内部密钥与服务凭证；
9. 启动授权中心、打包中心、Worker、数据库、队列和选定的反向代理；
10. 配置 HTTPS、证书申请和自动续期；Caddy 是现有/候选实现，不是用户锁定的唯一技术；
11. 等待全部健康检查通过；
12. 安装简洁的全局管理命令（现有候选为 /usr/local/bin/appgog），并输出管理地址和初始管理员凭证。

以下目录是现有方案/候选实现，需要先核对现有代码和迁移成本，不是用户锁死的路径：

/opt/appgog/                 程序目录
/opt/appgog/.env             主配置（严格权限）
/opt/appgog/backups/         备份目录
/opt/appgog/logs/            运维操作日志
/opt/appgog/runtime/         运行配置
/usr/local/bin/appgog        全局管理命令

菜单一级核心信息必须展示：

- APPGOG 版本和更新状态；
- 系统、Docker、数据库、Worker、队列状态；
- 授权中心平台地址和打包中心平台地址；
- 两个域名的 DNS、HTTPS、证书到期和自动续期状态；
- 磁盘、内存、备份和安全状态。

菜单核心功能：

- 查看系统状态；
- 启动、停止、重启全部服务；
- 查看指定服务日志；
- 修改并保存两个平台域名；
- 查看初始管理员凭证；
- 更新系统和版本回滚；
- 创建和恢复完整备份；
- HTTPS、DNS 和证书管理；
- Docker、网络、数据卷、数据库、Worker、队列检查；
- 系统诊断与安全修复；

- 导出诊断报告；

专业要求：

- 恢复前验证备份包；

十四、最低测试与验收标准

- 错误域名、Origin、Installation ID、Build、Package 或 License 失败；
- 已消费 Install Key、重放请求和并发安装解锁失败；
- Token 篡改、过期、撤销和 generation 变化失败；
- 离线宽限期和超期受限逻辑正确；
- 未激活时前端入口和所有关键服务端接口均受限。

部署运维：

十六、最终一句话定义
======================================================================

固定 License Key 代表客户的长期购买身份；客户在打包中心绑定授权域名并生成专属包；每个包具有独立的离线包身份和一次性 Install Key；ZIP 在 Xboard 中先使用一次性 Install Key 完成第一阶段安装解锁并立即作废，但正式功能仍锁定；随后在 APPGOG 后台输入固定 License Key，验证包身份、域名和安装环境后完成第二阶段正式激活，才接通 APPGOG 与 Xboard；激活后使用签名凭证本地验签并定期联网刷新，同时通过每包随机保护、完整性校验、环境绑定和构建水印提高复制与源码提取成本；授权中心始终管理业务，Linux 管理中心始终管理部署、运行与安全。
